# v1.0.0 验证记录

日期：2026-09-10。验证对象：本仓库的提示词 Skill。

## 实际做了什么

1. 使用 Codex 的 Skill 结构验证器 `quick_validate.py` 检查技能目录，结果为 `Skill is valid!`。
2. 在独立对话上下文中，让执行助手读取 Skill、必要参考文件及测试图片，顺序处理 12 个请求。执行者不读取评分表、README 或原始项目对话。12 例在同一上下文内执行，并非 12 次独立抽样。
3. 制作者在阅读输出前保存检查表，随后人工逐项复核。图片查看情况结合执行过程检查；记录中的 `images_viewed` 本身不是自动证明。
4. 公开原始请求、图片、完整输出、原检查表和逐项判定，保留不符合检查表的项目。

## 结果

| 项目 | 结果 |
| --- | --- |
| 技能结构验证 | 通过 |
| 已完成的行为场景 | 12 |
| 预设检查项 | 41 |
| 符合检查项 | 40 |
| 不符合检查项 | 1，见下文 |
| 全部符合检查表的场景 | 11 / 12 |
| 实际生图对照试验 | 未进行 |
| 首轮图片可用率、返工次数、耗时改善 | 未测量 |

**唯一未通过项是 C02 的检查表措辞过窄。**用户要求“红杯子改成蓝色”，实际输出把红色杯身和红色杯柄都改蓝，保留白色竖条；预设检查项却写成“仅要求将杯身改为蓝色”。按字面记为未通过。输出与用户要求并不冲突，但不能在看到结果后修改原检查表、再宣称全通过。后续应增加明确区分“整个杯子”和“仅杯身”的新用例。

其他观察：C05 在用户未要求逐像素保留时加入了相关提醒，回答还可以更简练。C07 缺少新背景和新衣服的目标，正确询问后给出分轮顺序及可先写出的第三轮指令；因此本项目不承诺任何输入都零追问。

## 如何复核

- [请求](../tests/cases.json)与[原检查表](../tests/rubric.json)
- [完整试用输出](../tests/results/forward-outputs.json)与[逐项人工判定](../tests/results/assessment.json)
- [自制图片](../tests/fixtures/)，未使用用户照片或私人项目截图。

在仓库根目录运行 `python3 tools/summarize_validation.py` 可重新汇总判定文件。这个脚本仅验证记录覆盖与计算数量，不会判断语义或图片质量。

## 不能由此推出什么

这是一轮小规模行为试用，未测自动触发的准确率，未在多种宿主和模型上验证，未做有无 Skill 的生图对照，也没有记录真实完成用时。部分素材和示例主题相近，因此不是严格的全新任务基准。评分由制作者复核，不是第三方认证。

不能把 40/41 写成“图片准确率”“效果提升比例”，也不能声称减少了多少出图次数。验证真实出图价值，需要固定任务、原图、图像模型和设置，对有无 Skill 的两组重复出图，记录首轮全部关键要求通过率、返工次数、保留项和真实用时，并公开失败结果。
